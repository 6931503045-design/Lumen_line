1. Introduction

1.1 Purpose and scope

University students run out of money before the end of the month without being able to say where it went. Two things cause this. First, logging an expense in a normal finance app takes four steps — open the app, pick a category, type the amount, save — so students stop logging within two or three weeks and the record is never complete enough to act on. Second, even a complete record only answers "where did my money go", which is a report about the past; it does not answer the question a student actually asks, which is "how much can I still spend today without breaking the month".

JOD tang answers exactly two questions: "How much can I still spend today?" and "I want this thing — how much do I need to save each month to afford it?" It removes the logging friction by living inside LINE, which students already have open: typing กาแฟ 80 ("coffee 80") in a chat records an 80-baht expense in about three seconds, and forwarded bank notification emails are parsed into transactions without the student doing anything at all. The MVP is five Must requirements. Success means a student reaches the end of the month knowing what they can spend, because the number was in front of them daily — not because they were disciplined about bookkeeping.

2.2 Assumptions and constraints

  • Assumption: every user already has LINE installed and uses it daily; identity is the LINE account, so there is no separate sign-up.
  • Assumption: the student can set up email forwarding from their bank app to the address the system gives them (a written guide is provided).
  • Constraint — money arithmetic: all amounts are stored as positive integers in satang (1/100 baht). Floating-point arithmetic is forbidden anywhere on a monetary path.
  • Constraint — AI boundary: AI may interpret language only. It must not compute, adjust or forecast any monetary figure, and it must not write to the database without an explicit human confirmation.
  • Constraint — AI must be optional: with the AI provider disabled, every Must requirement still works.
  • Constraint — LINE free tier: at most 280 push messages per user per month.
  • Constraint — data isolation: the database has row-level security enabled with no policies, so every query must filter by the signed-in user's id at the application layer.
  • Constraint — schedule: a 10-week build window shared with four other milestones (M1–M5); team of five.

3.2 FR-1 — Log an expense from a chat message [Must]

User story: As a student on a fixed allowance, I want to log a purchase by typing one short message in LINE, so that logging costs me so little effort that I actually keep doing it past week three.

Pain this traces to: logging in a normal finance app takes four steps, so students abandon it within two or three weeks and the record is never complete enough to trust.

  1. Given a student sends the message กาแฟ 80, when the system parses it, then an expense of exactly 8000 satang is stored against that student with the category "Food", and the reply states the amount and category.
  2. Given a student sends เงินเดือน 15000 ("salary 15000"), when the system parses it, then the row is stored as income, not as an expense.
  3. Given a student sends ข้าว 1.2k, when the system parses it, then the amount is read as 1,200 baht (120000 satang).
  4. Wrong path. Given a student sends a message with no number in it, when the system parses it, then nothing is written to the ledger and the reply shows an example of the accepted format.
  5. Wrong path. Given a student sends กาแฟ -80, when the system parses it, then the message is rejected and no row is created, because stored amounts are positive integers only.
  6. Wrong path. Given a student sends an amount above 10,000,000 baht, when the system parses it, then the message is rejected and the reply states the per-transaction ceiling.

3.3 FR-2 — Import bank notification emails [Must]

User story: As a student who pays by bank transfer, I want the notification emails my bank already sends me to become transactions by themselves, so that the spending I forget to type is still on the record.

Pain this traces to: the expenses a student forgets are exactly the ones that break the month, and a student who just paid is the least likely person to stop and type it in.

  1. Given a K PLUS notification email for a 131.00-baht payment is forwarded to the student's ingest address, when the next poll runs, then an expense of 13100 satang is created for that student within five minutes.
  2. Given the email reached the system through Gmail forwarding, when its signature is checked, then DKIM still verifies and the email is accepted.
  3. Wrong path. Given an email whose DKIM signature does not verify, when it is processed, then it is skipped and no transaction is created, so that a forged notification cannot inject a row.
  4. Wrong path. Given an email arriving at an address with no valid ingest token, when it is processed, then it is skipped, because the system cannot tell whose ledger it belongs to.
  5. Wrong path. Given an email that has already been imported, when the same email is fetched again, then no duplicate transaction is created.

3.4 FR-3 — Daily safe-to-spend figure [Must]

User story: As a student deciding whether to buy something right now, I want one number telling me what I can still spend today, so that I can decide in two seconds instead of reading a report about last month.

Pain this traces to: a list of past transactions does not answer "can I afford this today"; the student has to do the arithmetic, which nobody does at the till.

Definition: remaining = income this month + scheduled income not yet posted − expenses this month − scheduled expenses not yet posted − the monthly saving amount of every active plan. Per-day = remaining ÷ days left in the month, counting today, in Asia/Bangkok. Computed fresh on every request; no AI involved.

  1. Given a student has 3,000 baht remaining and 10 days left in the month, when they ask how much they can spend, then the answer is 300 baht per day.
  2. Given the student has an active saving plan of 1,000 baht per month, when the figure is computed, then that 1,000 baht is subtracted before the division, so the plan is not silently spent.
  3. Given today is the last day of the month, when the figure is computed, then the divisor is 1 and the calculation does not fail.
  4. Wrong path. Given the student has already overspent and the remaining amount is negative, when the figure is shown, then the screen states how much they are over by and does not present a negative number as a daily allowance.
  5. Wrong path. Given a student with fewer than seven days of history, when the figure is shown, then it carries a low-confidence label, because a number from three days of data is not yet trustworthy.

3.5 FR-4 — Category budget with 80% / 100% alerts [Must]

User story: As a student who overspends on food without noticing, I want to be warned while I still have money left, so that I can change what I do this week rather than discover the problem when the month is over.

Pain this traces to: overspending is discovered at the end of the month, when nothing can be done about it.

  1. Given a 3,000-baht monthly food budget and 2,400 baht already spent, when the next food expense is recorded, then the student is warned that 80% of the budget is used, exactly once for that month.
  2. Given the 80% warning has already been sent and spending reaches 3,000 baht, when the next expense is recorded, then a 100% warning is sent once and the 80% warning is not repeated.
  3. Given the student changes the budget amount, when the new amount is saved, then both warnings become available again for that month.
  4. Wrong path. Given spending stands at 79.99966% of the budget, when the threshold is evaluated, then no warning is sent, because a rounded percentage must not trigger the alert early and consume the month's single warning.
  5. Wrong path. Given a request to set a budget of zero or a negative amount, when it is submitted, then it is rejected.
  6. Wrong path. Given a request to set a budget on a category belonging to another student, when it is submitted, then it fails as not found, without revealing that the category exists.

3.6 FR-5 — Saving plan with three options [Must]

User story: As a student who wants to buy a 25,000-baht laptop, I want to be shown what saving for it would actually cost me per month, so that I can commit to a plan I can keep instead of guessing and abandoning it.

Pain this traces to: students set a savings goal by wishful thinking, miss it in month two, and stop saving entirely.

  1. Given a student sets a target of 25,000 baht, when the system builds the plan, then it offers exactly three options, each stating a monthly amount, a finish month and a confidence level, all derived from that student's own recorded income and spending.
  2. Given the three options are shown, when the student confirms one, then that plan becomes active and the other two are discarded.
  3. Wrong path. Given the student has not confirmed any option, when the safe-to-spend figure is computed, then the unconfirmed plan is not subtracted, because nothing was agreed to.
  4. Wrong path. Given the student already has three active plans, when they try to create a fourth, then it is refused with the reason stated.
  5. Wrong path. Given the student's recorded spending leaves nothing to save each month, when a plan is requested, then the system says the target is not reachable yet instead of inventing a monthly figure.

6. Out of scope

  1. Connecting to any bank API or Open Banking service — outside what a student team can be authorised for.
  2. Investment, stock or cryptocurrency tracking — does not serve either question in §1.1.
  3. Any currency other than Thai baht.
  4. Charging users; any payment, subscription or advertising feature.
  5. A native mobile app or a standalone web app outside LINE.
  6. AI computing, adjusting or forecasting any monetary figure.
  7. General-purpose conversation with the AI beyond clarifying questions.
  8. Statistical forecasting such as Monte Carlo simulation or seasonality modelling.
