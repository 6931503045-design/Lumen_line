## 1. บทนำและวัตถุประสงค์

### 1.1 ปัญหา

1. **จดแล้วเลิก** — แอปจดรายจ่ายทั่วไปต้องกรอกหลายขั้นตอน (เปิดแอป → เลือกหมวด → พิมพ์ยอด → บันทึก)
   ผู้ใช้ส่วนใหญ่เลิกจดภายใน 2–3 สัปดาห์
2. **รู้แค่ว่าเงินหายไปไหน** — แอปบอกได้ว่าเดือนนี้ใช้ไปเท่าไหร่ แต่ไม่ตอบคำถามที่ผู้ใช้อยากรู้จริง ๆ

### 1.2 สิ่งที่ระบบนี้ต้องตอบให้ได้

ทั้งโปรเจกต์มีอยู่เพื่อตอบ **2 คำถาม**:

> **คำถามที่ 1 — "วันนี้ฉันใช้เงินได้อีกเท่าไหร่?"**
> **คำถามที่ 2 — "อยากได้สิ่งนี้ ต้องออมเดือนละเท่าไหร่ถึงจะไหว?"**

ทุก FR ในเอกสารนี้ต้องโยงกลับไปหาคำถามใดคำถามหนึ่ง ไม่งั้นถือว่าอยู่นอกขอบเขต

### 1.3 แนวทางแก้ — สามเสาหลัก

| เสา | แนวทาง | FR ที่รองรับ |
|---|---|---|
| **A — จดง่ายที่สุด** | พิมพ์ `กาแฟ 80` ใน LINE / ให้อีเมลธนาคารไหลเข้าเอง | FR-01, FR-02, FR-03 |
| **B — วางแผนที่ทำได้จริง** | คำนวณจากพฤติกรรมจริง เสนอแผนที่ไม่ทำให้ชีวิตลำบาก | FR-05, FR-06, FR-07, FR-08 |
| **C — AI เข้าใจภาษาคน แต่ไม่แตะตัวเลข** | AI ตีความข้อความ · โค้ดคำนวณเงินทุกบาท | FR-14 (Should) |

## 2. ผู้ใช้และผู้มีส่วนได้ส่วนเสีย

### 2.1 ผู้ใช้หลัก (Primary user)

**นักศึกษามหาวิทยาลัย อายุ 18–24 ปี ที่มีเงินจำกัดต่อเดือน**

| ลักษณะ | รายละเอียด |
|---|---|
| รายได้ | เงินจากผู้ปกครองเป็นก้อน/เดือน + งานพาร์ทไทม์บ้าง |
| พฤติกรรม | ใช้ LINE ทุกวัน · จ่ายเงินผ่านแอปธนาคาร (K PLUS) · ไม่เปิดแอปการเงินแยก |
| ความเจ็บปวด | สิ้นเดือนเงินหมดโดยไม่รู้ว่าหมดไปกับอะไร · อยากได้ของแต่ไม่รู้ว่าเก็บไหวไหม |
| ทำไมต้องเป็น LINE | ผู้ใช้อยู่ใน LINE อยู่แล้ว — จดได้ใน 3 วินาทีโดยไม่ต้องเปิดแอปใหม่ |

| อาจารย์ผู้สอน | ความผูกกันของเอกสาร ↔ โค้ด (Golden Thread) |

## 3. ขอบเขต

### 3.1 อยู่ในขอบเขต (In scope)

- บันทึกรายรับ/รายจ่ายผ่าน **แชท LINE** และ **อีเมลธนาคาร** (K PLUS)
- คำนวณ **เงินที่ใช้ได้ต่อวัน** จากพฤติกรรมจริง
- **งบรายหมวด** พร้อมเตือนเมื่อใช้ถึง 80% และ 100%
- **แผนออม** เสนอ 3 ทางเลือก + ติดตามความคืบหน้า
- **หน้าเว็บ 5 หน้า** ใน LINE (LIFF) สำหรับดูกราฟและจัดการข้อมูล
- สกุลเงิน **บาทเท่านั้น**

### 3.2 อยู่นอกขอบเขต (Out of scope)

| ไม่ทำ | เหตุผล |
|---|---|
| ❌ เชื่อม API ธนาคาร / Open Banking | ต้องขออนุญาตระดับสถาบัน เกินขอบเขตวิชา |
| ❌ ติดตามการลงทุน หุ้น คริปโต | ไม่ตอบ 2 คำถามหลัก |
| ❌ หลายสกุลเงิน | ผู้ใช้เป้าหมายใช้บาทอย่างเดียว |
| ❌ เก็บเงินผู้ใช้ / เชิงพาณิชย์ | เป็นโปรเจกต์การศึกษา |
| ❌ แอป native / เว็บแอปแยก | ใช้ LIFF ใน LINE แทน ลดแรงเสียดทานการเข้าใช้ |
| ❌ **AI คำนวณเงินหรือพยากรณ์ตัวเลข** | ⚖️ กฎเหล็ก G1 — AI ไม่แตะตัวเลขเงิน |
| ❌ แชทคุยเล่นทั่วไป | AI ตอบได้เฉพาะคำถามกลับเพื่อความชัดเจน |
| ❌ พยากรณ์เชิงสถิติขั้นสูง (Monte Carlo) | เกินความจำเป็นของ MVP |

### 3.3 กฎเหล็ก 7 ข้อที่ผูกทุก requirement

ทุก FR/NFR ต้องไม่ขัดกับกฎเหล่านี้ (รายละเอียดเต็มใน `docs/RULES.md`)

| กฎ | ใจความ |
|---|---|
| **G1** | AI ไม่คำนวณเงิน — ตัวเลขทุกบาทมาจากโค้ดใน Money Engine |
| **G2** | AI จะแตะข้อมูลต้องมีคนกดยืนยันก่อน (ผู้ใช้กดปุ่มเอง = ยืนยันแล้ว) |
| **G3** | เงินเก็บเป็นจำนวนเต็มหน่วย**สตางค์** เป็นบวกเสมอ ห้ามใช้ float |
| **G4** | ปิด AI แล้วแอปต้องยังใช้ได้ |
| **G5** | ลบข้อมูลส่วนตัวออกก่อนส่งให้ AI |
| **G6** | ทุก query ต้องกรอง `user_id` จากแหล่งที่เซ็นแล้ว |
| **G7** | การโอนเข้าแผน (`transfer`) ไม่นับเป็นรายรับและไม่นับเป็นรายจ่าย |

## 4. ความต้องการเชิงฟังก์ชัน (FR)

### 4.1 การจัดลำดับ MoSCoW

> **Must = MVP** — ถ้าขาดข้อใดข้อหนึ่ง ระบบตอบ 2 คำถามหลักไม่ได้

| ระดับ | จำนวน | ความหมาย |
|---|---|---|
| **Must** | 8 (FR-01…FR-08) | ขาดไม่ได้ — prototype ต้องครอบทุกตัว |
| **Should** | 6 (FR-09…FR-14) | ทำให้ใช้งานสะดวกขึ้นมาก แต่ตัดออกแล้วยังตอบ 2 คำถามได้ |
| **Could** | 6 (FR-15…FR-20) | มีก็ดี ทำทีหลังได้ |

### 4.2 Must — MVP (FR-01 … FR-08)

| ID | ความต้องการ | ผู้ใช้ได้อะไร | ตอบคำถามข้อ |
|---|---|---|---|
| **FR-01** | ผู้ใช้พิมพ์ข้อความสั้นใน LINE เช่น `กาแฟ 80` แล้วระบบบันทึกเป็นรายจ่ายพร้อมหมวดทันที | จดได้ใน 3 วินาที ไม่ต้องเปิดแอปใหม่ | 1 |
| **FR-02** | อีเมลแจ้งเตือนจากธนาคาร (K PLUS) ที่ forward เข้ามา ถูกแปลงเป็นรายการอัตโนมัติ | ไม่ต้องจดเอง เงินออกก็ขึ้นเอง | 1 |
| **FR-03** | ผู้ใช้เพิ่ม แก้ไข และลบรายการเงินได้จากหน้าเว็บ | แก้ที่ระบบอ่านผิดได้ ข้อมูลจึงเชื่อถือได้ | 1 |
| **FR-04** | ผู้ใช้ดูยอดคงเหลือ รายรับ รายจ่าย รายการล่าสุด และกราฟสัดส่วนรายหมวดได้ | เห็นภาพรวมว่าเงินไปไหน | 1 |
| **FR-05** | ระบบบอกว่า **"วันนี้ใช้ได้อีกวันละเท่าไหร่"** คำนวณจากเงินคงเหลือเดือนนี้หารด้วยจำนวนวันที่เหลือ | ตอบคำถามที่ 1 ตรง ๆ | **1** |
| **FR-06** | ผู้ใช้ตั้งงบรายเดือนต่อหมวดได้ และระบบเตือนเมื่อใช้ถึง 80% และ 100% | รู้ตัวก่อนใช้เกิน ไม่ใช่รู้ตอนสิ้นเดือน | 1 |
| **FR-07** | ผู้ใช้ตั้งเป้าหมายออม แล้วระบบเสนอ **3 ทางเลือก** (เร็ว / กลาง / สบาย) พร้อมยอดออมต่อเดือนและระดับความมั่นใจ | ตอบคำถามที่ 2 ตรง ๆ | **2** |
| **FR-08** | ผู้ใช้โอนเงินเข้าแผนออมได้ และเห็นความคืบหน้า พร้อมถูกเตือนเมื่อหลุดเป้าหรือครบเป้า | รู้ว่าแผนยังไหวอยู่ไหม | 2 |

### 4.3 Should (FR-09 … FR-14)

| ID | ความต้องการ | ทำไมไม่ใช่ Must |
|---|---|---|
| **FR-09** | รายการประจำ (เงินเดือน ค่าหอ ค่าเน็ต) ถูกบันทึกให้เองตามรอบ | จดเองได้ผ่าน FR-01 แค่เสียเวลากว่า |
| **FR-10** | ผู้ใช้เพิ่ม แก้ไข ลบ หมวดหมู่ของตัวเองได้ | มีหมวดเริ่มต้น 12 หมวดให้แล้ว ใช้ได้ทันที |

| **FR-14** | **AI (Gemini) ช่วยตีความข้อความที่ regex อ่านไม่ออก** พร้อม flow กดยืนยันก่อนบันทึก (⚖️ G2) | ⚖️ **G4 บังคับว่าปิด AI แล้วแอปต้องใช้ได้** → ตามนิยามจึงไม่ใช่ MVP |

> ข้อยกเว้นนั้นคือคำจำกัดความของ "ไม่ใช่ MVP" — เอกสารนี้จึงจัด FR-14 เป็น **Should** ให้ตรงกับ G4
> (ดูตารางเทียบทั้งหมดใน **ผนวก ค**)

> ทุกข้อเป็น **ตัวเลขที่วัดได้** ไม่ใช่คำคุณศัพท์ — "เร็ว" "ปลอดภัย" ใช้ไม่ได้

| **NFR-02** | ความแม่นยำของจำนวนเงิน (⚖️ G3) | คลาดเคลื่อน **0 สตางค์** — ไม่มี float ในเส้นทางคำนวณเงิน | `tests/money.test.ts` — ทุกยอดเป็น integer |
| **NFR-03** | แรงเสียดทานในการจด | บันทึก 1 รายการจากแชท ≤ **1 ข้อความ** และ ≤ **3 วินาที** | จับเวลาจากพิมพ์จบถึงได้ reply |
| **NFR-04** | ความหน่วงของการรับอีเมลธนาคาร | รายการขึ้นระบบภายใน ≤ **5 นาที** นับจากอีเมลเข้า | cron `*/5 * * * *` — ดู log GitHub Actions |
| **NFR-05** | โควตา push ของ LINE | ≤ **280 ครั้ง/เดือน** ต่อผู้ใช้ 1 คน | `push_log` + `tests/push.service.test.ts` |
| **NFR-06** | ผลลัพธ์คงเส้นคงวา | เรียกซ้ำด้วยข้อมูลชุดเดิม ได้ผลเหมือนเดิม **100%** | Money Engine ไม่มี `Math.random()` / ไม่เรียก AI |
| **NFR-07** | ไม่นับรายการซ้ำ | รายการเดียวกันจาก 2 ช่องทางภายใน **30 นาที** นับ **1 ครั้ง** | `tests/dedup.service.test.ts` |
| **NFR-08** | การแยกข้อมูลระหว่างผู้ใช้ (⚖️ G6) | **0 endpoint** ที่อ่าน/เขียนโดยไม่กรอง `user_id` | ทุกตารางเปิด RLS · ทุก query มี `.eq('user_id', …)` |
| **NFR-09** | เพดานจำนวนเงินต่อรายการ | ≤ **10,000,000 บาท** (1,000,000,000 สตางค์) | `CHECK` ใน DB + `assertTransactionAmount()` |
| **NFR-10** | ความลับของข้อมูล | **0 secret** ใน repo · ข้อมูลส่วนตัวถูกลบก่อนส่ง AI (⚖️ G5) | `.gitignore` + `tests/redact.test.ts` |
| **NFR-11** | ความครอบคลุมของการทดสอบ | **433 tests ผ่าน 433** (ณ 23 ก.ย. 2026) | `npm test` |

### FR-05 — ใช้ได้วันละเท่าไหร่ (คำถามที่ 1)

สูตร (🔴 Money Engine — ห้ามมี AI):

```
คงเหลือเดือนนี้ = รายรับเดือนนี้
                + recurring รายรับที่ยังไม่ถึงรอบ
                − รายจ่ายเดือนนี้
                − recurring รายจ่ายที่ยังไม่ถึงรอบ
                − Σ monthly_save ของแผนที่ active

ใช้ได้ต่อวัน = คงเหลือเดือนนี้ ÷ จำนวนวันที่เหลือในเดือน (นับวันนี้ด้วย, เวลาไทย)
```

| # | สถานการณ์ | คาดหวัง | ผล |
|---|---|---|---|
| ✅ 1 | คงเหลือ 3,000 บาท เหลือ 10 วัน | ตอบ **300 บาท/วัน** | ผ่าน |
| ✅ 2 | มีแผนออม active ยอด 1,000/เดือน | หัก 1,000 ออกก่อนหาร | ผ่าน |
| ✅ 3 | วันสุดท้ายของเดือน | หารด้วย 1 ไม่ใช่หารด้วย 0 | ผ่าน |
| ❌ 4 | ใช้เกินแล้ว (คงเหลือติดลบ) | เตือนว่า**ใช้เกินไปเท่าไหร่** ไม่แสดงเลขติดลบเป็นยอดใช้ได้ | ผ่าน |
| ❌ 5 | ผู้ใช้ใหม่ ข้อมูลน้อยกว่า 7 วัน | บอก**ระดับความมั่นใจต่ำ** ไม่ใช่ตอบตัวเลขลอย ๆ | ผ่าน |

## 7. ข้อจำกัด สมมติฐาน และความเสี่ยง

### 7.1 ข้อจำกัดทางเทคนิค

| ข้อจำกัด | ผลต่อ requirement |
|---|---|
| LINE free tier ส่ง push ได้ 280 ครั้ง/เดือน | NFR-05 · FR-12 ต้องมีระบบจัดลำดับความสำคัญ |
| Supabase เปิด RLS โดยไม่มี policy | การกรอง `user_id` เป็นหน้าที่ของ backend 100% (NFR-08) |
| GitHub Actions `schedule` ทำงานจาก default branch เท่านั้น | งานตามเวลาต้อง merge เข้า `main` ถึงจะทำงานจริง |
| Render free tier หลับเมื่อไม่มีคนใช้ | request แรกหลังหลับช้ากว่าปกติ |
| Gmail ตัด `+token` ออกจาก `Delivered-To` | FR-02 ต้องอ่าน `X-Forwarded-To` แทน |

### 7.2 สมมติฐาน

1. ผู้ใช้มี LINE และใช้งานเป็นประจำ
2. ผู้ใช้ตั้งค่า forward อีเมลจากธนาคารเองได้ (มีคู่มือ `docs/EMAIL_SETUP.md`)
3. รูปแบบอีเมลของ K PLUS ไม่เปลี่ยนบ่อย
4. ผู้ใช้ 1 บัญชี LINE = ผู้ใช้ 1 คน (ไม่มีบัญชีใช้ร่วมกัน)

### 7.3 ความเสี่ยง

| ความเสี่ยง | ผลกระทบ | การรับมือ |
|---|---|---|
| ธนาคารเปลี่ยนรูปแบบอีเมล | FR-02 พัง | ตัว parser แยกไฟล์ + มี fixture test · ยังจดมือผ่าน FR-01 ได้ |
| AI ตีความผิดแล้วบันทึกผิด | ข้อมูลเงินเพี้ยน | ⚖️ G2 ต้องกดยืนยันก่อนเสมอ · ⚖️ G1 AI ไม่แตะตัวเลข |
| โควตา push หมดกลางเดือน | เตือนไม่ถึงผู้ใช้ | NFR-05 กันโควตา 20% ไว้ให้เรื่องด่วน |
| ผู้ใช้ใหม่ข้อมูลน้อย แผนจึงไม่แม่น | ผู้ใช้เชื่อตัวเลขผิด | ติดป้ายระดับความมั่นใจทุกครั้ง (cold-start) |
