# ร่าง §S5.10 — เพดานการใช้จ่ายที่ผู้ใช้ตั้งเอง

> **สถานะ: ร่าง รอทีมรีวิว ยังไม่ใส่ลง SPEC.md** (ยืนยัน 2026-09-20 ว่าจะรอรีวิวก่อน) — ให้ทีมรีวิว โดยเฉพาะ ② Database (เจ้าของ budget service)
> และ ① Bot Core (เจ้าของ push quota) จุดที่ผมตัดสินใจเองอยู่ในหัวข้อ "ข้อที่ต้องยืนยัน" ท้ายไฟล์
>
> ที่มา: ทีมตกลงกันเมื่อ 2026-09-20 — ผู้ใช้เลือกได้ว่าจะให้ระบบคำนวณหรือตั้งเอง,
> แต่ละระดับผิดกฎแยกกัน, สัปดาห์เริ่มวันอาทิตย์, เตือนอย่างเดียวไม่บล็อก, ทดสอบ 5 คน เตือน ~21:00

## จุดประสงค์

ให้ผู้ใช้กำหนดเพดานการใช้จ่ายได้ 3 ระดับ: **รายวัน / รายสัปดาห์ / รายเดือน**
ต่างจาก §S5.8 งบรายหมวด ตรงที่อันนี้เป็นเพดาน **รวมทุกหมวด** และมีระดับวัน/สัปดาห์ด้วย

## ของเดิมที่เกี่ยวข้อง (อย่าทำซ้ำ)

| ของเดิม | ทำอะไรอยู่ | ต่างกันยังไง |
|---|---|---|
| §S5.2 Safe-to-spend | คำนวณ "ใช้ได้วันนี้เท่าไร" ให้อัตโนมัติ | เป็นตัวเลขที่ระบบคิดให้ ไม่ใช่เพดานที่ผู้ใช้ตั้ง — **โหมด system ของฟีเจอร์นี้ใช้ค่านี้เป็นฐาน** |
| §S5.8 งบรายหมวด | เพดานรายเดือน **ต่อหมวด** + เตือน 80%/100% | แยกหมวด ไม่ใช่ยอดรวม และไม่มีระดับวัน/สัปดาห์ |

## S5.10.1 โหมด

ผู้ใช้เลือกได้ต่อระดับ (ตั้งรายวันเป็น system แต่รายเดือนเป็น manual ได้)

| โหมด | เพดานมาจาก |
|---|---|
| `manual` | ตัวเลขที่ผู้ใช้กรอกเอง คงที่ทุกงวด |
| `system` | ระบบคำนวณจาก §S5.2 แล้ว **ตรึงไว้ตอนเริ่มงวด** (ดู S5.10.2) |

แต่ละระดับเปิด/ปิดแยกกันได้ ไม่เปิดเลยก็ได้ (ฟีเจอร์นี้เป็น opt-in)

## S5.10.2 สูตรของโหมด `system`

ฐานร่วม — ใช้ค่าจาก §S5.2 ตรงๆ ไม่คิดสูตรใหม่

```
R = คงเหลือเดือนนี้ (นิยามตาม §S5.2)
D = จำนวนวันที่เหลือในเดือน นับวันนี้ด้วย (เวลาไทย)
ใช้ได้ต่อวัน = R ÷ D        ← คือ safe-to-spend เดิม
```

### การตรึงค่า

เพดานของรายวันและรายสัปดาห์ **ตรึงไว้ตอนเริ่มงวด** ส่วนรายเดือนคำนวณสด

> 🔴 **R และ D ต้องคิด "ณ ต้นงวด" เสมอ** คือไม่นับรายการที่ `occurred_at` อยู่ในงวดนั้น
> ไม่ใช่ค่า ณ เวลาที่โค้ดบังเอิญไปสร้างแถวงวด — ไม่งั้นเพดานจะต่างกันตามเวลาที่ผู้ใช้เปิดแอป
> ครั้งแรกของวัน ซึ่งขัดกติกาของ §S5 ที่ว่า "ให้ผลเหมือนเดิมทุกครั้งเมื่อข้อมูลเหมือนเดิม"
>
> ระบบไม่มี job ตอนเที่ยงคืน ให้**สร้างแถวงวดแบบ lazy** คือสร้างตอนถูกอ่าน/ถูกเทียบครั้งแรก
> แต่คำนวณด้วยข้อมูล ณ ต้นงวดตามข้างบน ผลจึงเท่ากันไม่ว่าจะสร้างตอนไหน
>
> ผลข้างเคียง: รายรับที่ผู้ใช้จดเพิ่มระหว่างงวดจะไปมีผลกับงวดถัดไป ไม่ใช่งวดปัจจุบัน
> กรณีรายรับประจำ (เงินเดือน/เงินที่บ้านโอน) ไม่กระทบ เพราะ §S5.2 นับ recurring ที่ยังไม่ถึงรอบไว้ล่วงหน้าอยู่แล้ว

### รายวัน

```
เพดานรายวัน = R ÷ D        (ค่า ณ ต้นวัน)
```

### รายสัปดาห์ (แบบ B — เติมเมื่อขึ้นเดือนใหม่)

สัปดาห์ที่คาบสองเดือนต้องคิดแยกตามอัตราของแต่ละเดือน

```
เพดานรายสัปดาห์ = ส่วนของเดือนแรก + ส่วนของเดือนที่สอง

ส่วนของเดือนแรก   = (R₁ ÷ D₁) × n₁
    R₁, D₁ = ค่า ณ วันเริ่มสัปดาห์ (วันอาทิตย์)
    n₁     = จำนวนวันของสัปดาห์นี้ที่อยู่ในเดือนแรก

ส่วนของเดือนที่สอง = (R₂ ÷ D₂) × n₂        ← มีเฉพาะเมื่อสัปดาห์คาบเดือน
    R₂, D₂ = ค่า ณ วันที่ 1 ของเดือนใหม่
    n₂     = จำนวนวันของสัปดาห์นี้ที่อยู่ในเดือนใหม่
```

**ตัวอย่าง** อาทิตย์ 28 ก.ย. – เสาร์ 4 ต.ค. (ก.ย. มี 30 วัน)

| | คำนวณ | ได้ |
|---|---|---|
| ส่วน ก.ย. | `(900 ÷ 3) × 3` | ฿900 (= เงินที่เหลือทั้งหมดของ ก.ย. พอดี) |
| ส่วน ต.ค. (เติม 1 ต.ค.) | `(9,500 ÷ 31) × 4` | ฿1,225.81 |
| รวม | | **฿2,125.81** |

สัปดาห์ที่ไม่คาบเดือนจะมีแค่ส่วนแรกและ `n₁ = 7` ได้ผลเท่าสูตรง่ายๆ `(R ÷ D) × 7`

**ใครเติม:** ทำในงานรายวันตอน 06:00 ของวันที่ 1 **หลัง** job `recurring` สร้างรายรับประจำแล้ว
ถ้าเติมก่อน รายรับประจำของเดือนใหม่จะยังไม่ถูกนับ แล้วเพดานจะต่ำเกินจริง
(ต้องให้ ② ยืนยันว่าจะแทรกใน `recurringJob` เลย หรือแยกเป็น job ใหม่)

### รายเดือน

```
เพดานรายเดือน = ใช้ไปแล้วเดือนนี้ + R        (คำนวณสด ไม่ตรึง)
```

ยอดใช้ไปแล้วตัดกันเอง เหลือ `รายรับ + recurring รายรับ − recurring รายจ่าย − Σ monthly_save`
จึงคงที่ ไม่ขยับตามการใช้จ่าย และ "เกินเพดานรายเดือน" มีความหมายเท่ากับ `R < 0` ซึ่ง §S5.2 เตือนอยู่แล้ว

**ทำไมรายเดือนไม่ตรึง:** ถ้าตรึงตั้งแต่วันที่ 1 รายรับที่เข้ามากลางเดือนจะไม่ถูกนับ เพดานจะต่ำเกินจริงแล้วเตือนผิด

### กติกาที่ใช้กับทุกระดับ

- ปัดลงเป็นสตางค์ ตามกติการ่วมของ §S5
- **ถ้าคำนวณได้ติดลบ ให้ใช้ 0** (เกิดเมื่อ `R < 0` คือใช้เกินไปแล้ว) — ห้ามเก็บค่าติดลบลงตาราง
- ต้องมีข้อมูลย้อนหลังอย่างน้อย **7 วัน** จึงจะเลือกโหมด `system` ได้
  น้อยกว่านั้น `R` ยังไม่มีความหมายพอ ให้เปิดได้เฉพาะโหมด `manual`
  (สอดคล้องกับ §S2 ที่ให้กราฟแสดงข้อความแทนเมื่อข้อมูลน้อยกว่า 7 วัน และแนวทาง cold-start ของ §S5.3)

## S5.10.3 การนับยอดใช้จ่ายของงวด

- นับเฉพาะ `type='expense'` และ `deleted_at is null` (`transfer` ไม่เข้าข่ายอยู่แล้วเพราะเป็นคนละ `type` — G7)
- แบ่งงวดตามเวลาไทย `(occurred_at at time zone 'Asia/Bangkok')`
- **สัปดาห์เริ่มวันอาทิตย์** ตามปฏิทินไทย

> ⚠️ ในโค้ดมี `getWeekStartIso()` (`src/utils/thaiDate.ts`) อยู่แล้ว แต่มันนับ **วันจันทร์**
> และ `planCheck.service.ts` ใช้อยู่ตาม §S5.6 — **ห้ามแก้ฟังก์ชันเดิม** ให้เพิ่มตัวใหม่
> เช่น `getWeekStartSundayIso()` ไม่งั้นการเตือนแผนออมจะเปลี่ยนพฤติกรรมโดยไม่ตั้งใจ
>
> ⚠️ ใน SQL ห้ามใช้ `date_trunc('week', ...)` เพราะ Postgres ยึด ISO = วันจันทร์

## S5.10.4 แต่ละระดับแยกกัน

ใช้เกินรายวัน = ผิดเฉพาะกฎรายวัน ไม่กระทบสัปดาห์หรือเดือน
ระดับที่ยังไม่ถึงเพดานยังถือว่าปกติ

**ตัวอย่าง:** ตั้งรายวัน ฿300 รายสัปดาห์ ฿1,500 — วันจันทร์ใช้ ฿500
→ เกินรายวัน ฿200 (เตือน) / ใช้ไปในสัปดาห์ ฿500 จาก ฿1,500 (ปกติ)

## S5.10.5 เกินแล้วทำอะไร

**เตือนอย่างเดียว บันทึกรายการตามปกติเสมอ** — เหมือน §S5.8 ไม่มีการบล็อก

> เหตุผล: เงินถูกใช้ไปจริงแล้วตอนที่ผู้ใช้มาจด การปฏิเสธไม่ให้บันทึกไม่ได้ทำให้เงินกลับมา
> แต่ทำให้ข้อมูลในแอปผิดจากความจริง และขัดกับหลักของระบบที่ให้จดได้ใน 3 วินาที

เตือน 2 จังหวะ

| จังหวะ | ช่องทาง | โควตา |
|---|---|---|
| ทันทีที่บันทึกแล้วยอดข้ามเกณฑ์ | แนบไปใน reply เดิมที่ตอบผู้ใช้ (แบบ §S5.8) | **ฟรี ไม่กิน push** |
| สรุปตอน 21:00 | push (รวมกับสรุปรายวันถ้ามี) | กิน push quota §S13 |

เกณฑ์เตือน **80% และ 100%** ของแต่ละงวด เตือนอย่างละครั้งต่องวด (เหมือน `alerted_80`/`alerted_100` ของ §S5.8)

> 🔴 **ต้องรวมข้อความเตือนให้เหลือชิ้นเดียว** รายการเดียวอาจทำให้ข้ามเกณฑ์พร้อมกันหลายอัน
> (รายวัน + รายสัปดาห์ + รายเดือน = ได้ถึง 3 ข้อความ) และยังอาจชนกับการเตือนงบรายหมวดของ §S5.8
> ในรายการเดียวกันอีก ถ้าไม่รวม ผู้ใช้จะโดนยิงรัวจนเลิกสนใจ และเปลือง push quota (§S13)
> ให้รวบทุกเกณฑ์ที่ข้ามในรายการนั้นเป็นข้อความเดียว

`dedup_key` ของ push ใช้รูป `limit:<period>:<userId>:<period_start>:<threshold>`
เพื่ออาศัย `unique` ของ `push_log.dedup_key` กันส่งซ้ำ (ตาราง `push_log` ใน `001_init.sql`)

> ⚠️ `src/jobs/dailySummary.ts` ยังเป็นไฟล์เปล่า และยังไม่ได้ลงทะเบียนใน `src/jobs/index.ts`
> ถ้าจะเตือน 21:00 ต้องเขียน job นี้ก่อน นับเป็นงานเพิ่มในแผน

## S5.10.6 ตารางข้อมูล (migration `003_spending_limits.sql`)

```sql
-- ค่าที่ผู้ใช้ตั้งไว้ (ระดับละ 1 แถวต่อผู้ใช้)
create table spending_limits (
  id           uuid primary key default gen_random_uuid(),
  user_id      uuid not null references users(id) on delete cascade,
  period       text not null check (period in ('daily','weekly','monthly')),
  mode         text not null check (mode in ('system','manual')),
  limit_amount numeric(12,2) check (limit_amount > 0),
  enabled      boolean not null default true,
  created_at   timestamptz not null default now(),
  updated_at   timestamptz not null default now(),
  unique (user_id, period),
  -- โหมด manual ต้องมีตัวเลข / โหมด system ปล่อยว่างเพราะคำนวณเอา
  check (mode = 'system' or limit_amount is not null)
);

-- เพดานที่ตรึงไว้ของแต่ละงวด + สถานะการเตือน
create table spending_limit_periods (
  id           uuid primary key default gen_random_uuid(),
  user_id      uuid not null references users(id) on delete cascade,
  period       text not null check (period in ('daily','weekly','monthly')),
  period_start date not null,
  -- 0 ได้ (เกิดเมื่อ R ติดลบ = ใช้เกินไปแล้ว) แต่ติดลบไม่ได้
  limit_amount numeric(12,2) not null check (limit_amount >= 0),
  alerted_80   boolean not null default false,
  alerted_100  boolean not null default false,
  unique (user_id, period, period_start)
);
```

ต้องทำเพิ่มอีก 2 อย่าง

```sql
-- spending_limits มีคอลัมน์ updated_at จึงต้องผูก trigger เหมือนตารางอื่น
-- (ฟังก์ชัน set_updated_at() ถูกสร้างไว้แล้วใน 002_updated_at_trigger.sql)
drop trigger if exists trg_spending_limits_updated_at on spending_limits;
create trigger trg_spending_limits_updated_at
  before update on spending_limits
  for each row
  execute function set_updated_at();
```

- เปิด RLS ทั้งสองตารางเหมือนตารางอื่น (§8) และทุก query กรอง `user_id` (G6)
- `spending_limit_periods` สะสมแถวเรื่อยๆ (ผู้ใช้ 1 คน = 3 แถว/วันอย่างมาก) ควรให้ job `cleanup`
  ลบแถวที่เก่ากว่า 90 วันทิ้ง เหมือนที่ทำกับ log อื่น
- **แถวของระดับรายเดือนเก็บไว้เพื่อ `alerted_80`/`alerted_100` เท่านั้น** เพราะรายเดือนคำนวณสด
  ไม่ได้ตรึง ให้ถือว่า `limit_amount` ของแถวรายเดือนเป็นค่าที่คำนวณได้ล่าสุด (cache)
  และเขียนทับทุกครั้งที่ตรวจ ไม่ใช่ค่าที่ตรึงไว้เหมือนรายวัน/รายสัปดาห์

> 🔴 **ห้ามหารด้วย `limit_amount` ตรงๆ** เพราะเป็น 0 ได้ (เมื่อ `R` ติดลบ)
> ถ้าเพดานเป็น 0 ให้ถือว่าเกิน 100% ทันทีโดยไม่ต้องคำนวณเปอร์เซ็นต์

## S5.10.7 API

| Method | Path | ใช้ทำอะไร |
|---|---|---|
| GET | `/api/limits` | อ่านค่าที่ตั้งไว้ + เพดานงวดปัจจุบัน + ยอดใช้ไปแล้ว + % |
| PUT | `/api/limits/:period` | ตั้ง/แก้ (body: `mode`, `limitSatang`, `enabled`) |
| DELETE | `/api/limits/:period` | ลบการตั้งค่าของระดับนั้นทิ้ง |

`enabled=false` = เก็บตัวเลขไว้แต่หยุดเตือนชั่วคราว ส่วน `DELETE` = ลบทิ้งจริง ต้องตั้งใหม่ทั้งหมด

**หน้าเว็บห้ามคำนวณ % หรือยอดคงเหลือเอง (G1)** — ให้ API ส่ง `usedSatang`, `limitSatang`, `percentUsed` มาให้ครบ

## S5.10.8 หน้าเว็บ

- `settings.html` — ตั้งค่าทั้ง 3 ระดับ (เลือกโหมด + กรอกตัวเลขเมื่อเป็น manual)

- `analyze.html` — ตัวจำลองผลกระทบก่อนซื้อ (§S5.7) ควรเทียบกับเพดานนี้ด้วยเมื่อผู้ใช้เปิดใช้
  ไม่ใช่เทียบกับ safe-to-spend อย่างเดียวเหมือนตอนนี้

## S5.10.9 ข้อกำหนดอื่น

- ฟีเจอร์นี้**ไม่แตะ AI เลย** ทำงานได้ปกติเมื่อ `AI_ENABLED=false` (G4)
- เพดานเป็นจำนวนเต็มบวกเสมอ เก็บเป็นสตางค์ในโค้ด / `numeric(12,2)` ใน DB (G3)
- ทุก query กรอง `user_id` ที่มาจาก session ไม่ใช่จาก client (G6)
- ไม่ต้องผ่าน `pending_actions` เพราะผู้ใช้เป็นคนกดตั้งค่าเอง ไม่ใช่ AI เขียน (G2)

   ต้องให้ ② ยืนยัน เพราะเป็นเจ้าของไฟล์นั้น
3. **เพดานขัดกันเอง** เช่นตั้งรายวัน ฿300 (×7 = ฿2,100) แต่รายสัปดาห์ ฿1,500

4. **ตั้งเพดานกลางงวด** เช่นตั้งรายสัปดาห์ตอนวันพุธ — เสนอให้นับยอดที่ใช้ไปแล้ว
   ตั้งแต่วันอาทิตย์ที่ผ่านมาเลย (ไม่เฉลี่ยตามวันที่เหลือ) เพราะอธิบายง่ายกว่า
5. **ต้องมีข้อมูล 7 วันก่อนถึงใช้โหมด `system` ได้** — ตัวเลข 7 มาจาก §S2 (กราฟต้องแสดง
   ข้อความแทนเมื่อข้อมูลน้อยกว่า 7 วัน) ถ้าทีมอยากได้ตัวเลขอื่นให้เปลี่ยนตรงนี้
6. **ข้อจำกัดที่ควรรู้ก่อนทดสอบ** — ในโหมด `system` ทั้งสามระดับมาจาก `R` ตัวเดียวกัน

   ทุกระดับจะเตือนไล่ๆ กัน ไม่ได้เป็นอิสระต่อกันเหมือนโหมด `manual`
