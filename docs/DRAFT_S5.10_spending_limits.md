# ร่าง §S5.10 — เพดานการใช้จ่ายที่ผู้ใช้ตั้งเอง

> **สถานะ: ร่าง ยังไม่ได้ใส่ลง SPEC.md** — ให้ทีมรีวิวก่อน โดยเฉพาะ ② Database (เจ้าของ budget service)
> และ ① Bot Core (เจ้าของ push quota) จุดที่ผมตัดสินใจเองอยู่ในหัวข้อ "ข้อที่ต้องยืนยัน" ท้ายไฟล์
>
> ที่มา: ทีมตกลงกันเมื่อ 2026-09-20 — ผู้ใช้เลือกได้ว่าจะให้ระบบคำนวณหรือตั้งเอง,
> แต่ละระดับผิดกฎแยกกัน, สัปดาห์เริ่มวันอาทิตย์, เตือนอย่างเดียวไม่บล็อก, ทดสอบ 5 คน เตือน ~21:00

## จุดประสงค์

ให้ผู้ใช้กำหนดเพดานการใช้จ่ายได้ 3 ระดับ: **รายวัน / รายสัปดาห์ / รายเดือน**
ต่างจาก §S5.8 งบรายหมวด ตรงที่อันนี้เป็นเพดาน **รวมทุกหมวด** และมีระดับวัน/สัปดาห์ด้วย

## ของเดิมที่เกี่ยวข้อง (อย่าทำซ้ำ)

| ของเดิม | ทำอะไรอยู่ | ต่างกันยังไง |
|---|---|---|
| §S5.2 Safe-to-spend | คำนวณ "ใช้ได้วันนี้เท่าไร" ให้อัตโนมัติ | เป็นตัวเลขที่ระบบคิดให้ ไม่ใช่เพดานที่ผู้ใช้ตั้ง — **โหมด system ของฟีเจอร์นี้ใช้ค่านี้เป็นฐาน** |
| §S5.8 งบรายหมวด | เพดานรายเดือน **ต่อหมวด** + เตือน 80%/100% | แยกหมวด ไม่ใช่ยอดรวม และไม่มีระดับวัน/สัปดาห์ |

## S5.10.1 โหมด

ผู้ใช้เลือกได้ต่อระดับ (ตั้งรายวันเป็น system แต่รายเดือนเป็น manual ได้)

| โหมด | เพดานมาจาก |
|---|---|
| `manual` | ตัวเลขที่ผู้ใช้กรอกเอง คงที่ทุกงวด |
| `system` | ระบบคำนวณจาก §S5.2 แล้ว **ตรึงไว้ตอนเริ่มงวด** (ดู S5.10.2) |

แต่ละระดับเปิด/ปิดแยกกันได้ ไม่เปิดเลยก็ได้ (ฟีเจอร์นี้เป็น opt-in)

## S5.10.2 สูตรของโหมด `system`

ฐานร่วม — ใช้ค่าจาก §S5.2 ตรงๆ ไม่คิดสูตรใหม่

```
R = คงเหลือเดือนนี้ (นิยามตาม §S5.2)
D = จำนวนวันที่เหลือในเดือน นับวันนี้ด้วย (เวลาไทย)
ใช้ได้ต่อวัน = R ÷ D        ← คือ safe-to-spend เดิม
```

เพดานของแต่ละระดับ คำนวณ **ครั้งเดียวตอนเริ่มงวด** แล้วตรึงไว้จนจบงวด

| ระดับ | ตรึงเมื่อ | เพดาน |
|---|---|---|
| รายวัน | 00:00 ของวันนั้น | `R ÷ D` |
| รายสัปดาห์ | 00:00 วันอาทิตย์ | `(R ÷ D) × min(7, D)` |
| รายเดือน | ไม่ตรึง คำนวณสด | `ใช้ไปแล้วเดือนนี้ + R` |

**ทำไมต้องตรึง:** ถ้าคำนวณสดทุกครั้ง เพดานจะขยับตามการใช้จ่ายเอง จนไม่มีทาง "เกิน" ได้เลย
การตรึงทำให้เกินรายวันได้โดยไม่เกินรายสัปดาห์ ตามที่ทีมตกลงไว้ และทำให้เพดานของ
วันถัดไปลดลงจริงเมื่อวันนี้ใช้เกิน (เพราะ R ลดลง) ตามที่ทีมต้องการ

**ทำไมรายเดือนไม่ตรึง:** ถ้าตรึงตั้งแต่วันที่ 1 รายรับที่เข้ามากลางเดือนจะไม่ถูกนับ
เพดานจะต่ำเกินจริงแล้วเตือนผิด — รายเดือนจึงคำนวณสด และ "เกินเพดานรายเดือน"
มีความหมายเท่ากับ `R < 0` ซึ่ง §S5.2 เตือนอยู่แล้ว

ปัดลงเป็นสตางค์ ตามกติการ่วมของ §S5

## S5.10.3 การนับยอดใช้จ่ายของงวด

- นับเฉพาะ `type='expense'`, `deleted_at is null`, ไม่รวม `transfer` (G7)
- แบ่งงวดตามเวลาไทย `(occurred_at at time zone 'Asia/Bangkok')`
- **สัปดาห์เริ่มวันอาทิตย์** ตามปฏิทินไทย

> ⚠️ ในโค้ดมี `getWeekStartIso()` (`src/utils/thaiDate.ts`) อยู่แล้ว แต่มันนับ **วันจันทร์**
> และ `planCheck.service.ts` ใช้อยู่ตาม §S5.6 — **ห้ามแก้ฟังก์ชันเดิม** ให้เพิ่มตัวใหม่
> เช่น `getWeekStartSundayIso()` ไม่งั้นการเตือนแผนออมจะเปลี่ยนพฤติกรรมโดยไม่ตั้งใจ
>
> ⚠️ ใน SQL ห้ามใช้ `date_trunc('week', ...)` เพราะ Postgres ยึด ISO = วันจันทร์

## S5.10.4 แต่ละระดับแยกกัน

ใช้เกินรายวัน = ผิดเฉพาะกฎรายวัน ไม่กระทบสัปดาห์หรือเดือน
ระดับที่ยังไม่ถึงเพดานยังถือว่าปกติ

**ตัวอย่าง:** ตั้งรายวัน ฿300 รายสัปดาห์ ฿1,500 — วันจันทร์ใช้ ฿500
→ เกินรายวัน ฿200 (เตือน) / ใช้ไปในสัปดาห์ ฿500 จาก ฿1,500 (ปกติ)

## S5.10.5 เกินแล้วทำอะไร

**เตือนอย่างเดียว บันทึกรายการตามปกติเสมอ** — เหมือน §S5.8 ไม่มีการบล็อก

> เหตุผล: เงินถูกใช้ไปจริงแล้วตอนที่ผู้ใช้มาจด การปฏิเสธไม่ให้บันทึกไม่ได้ทำให้เงินกลับมา
> แต่ทำให้ข้อมูลในแอปผิดจากความจริง และขัดกับหลักของระบบที่ให้จดได้ใน 3 วินาที

เตือน 2 จังหวะ

| จังหวะ | ช่องทาง | โควตา |
|---|---|---|
| ทันทีที่บันทึกแล้วยอดข้ามเกณฑ์ | แนบไปใน reply เดิมที่ตอบผู้ใช้ (แบบ §S5.8) | **ฟรี ไม่กิน push** |
| สรุปตอน 21:00 | push (รวมกับสรุปรายวันถ้ามี) | กิน push quota §S13 |

เกณฑ์เตือน **80% และ 100%** ของแต่ละงวด เตือนอย่างละครั้งต่องวด (เหมือน `alerted_80`/`alerted_100` ของ §S5.8)

> ⚠️ `src/jobs/dailySummary.ts` ยังเป็นไฟล์เปล่า และยังไม่ได้ลงทะเบียนใน `src/jobs/index.ts`
> ถ้าจะเตือน 21:00 ต้องเขียน job นี้ก่อน นับเป็นงานเพิ่มในแผน

## S5.10.6 ตารางข้อมูล (migration `003_spending_limits.sql`)

```sql
-- ค่าที่ผู้ใช้ตั้งไว้ (ระดับละ 1 แถวต่อผู้ใช้)
create table spending_limits (
  id           uuid primary key default gen_random_uuid(),
  user_id      uuid not null references users(id) on delete cascade,
  period       text not null check (period in ('daily','weekly','monthly')),
  mode         text not null check (mode in ('system','manual')),
  limit_amount numeric(12,2) check (limit_amount > 0),
  enabled      boolean not null default true,
  created_at   timestamptz not null default now(),
  updated_at   timestamptz not null default now(),
  unique (user_id, period),
  -- โหมด manual ต้องมีตัวเลข / โหมด system ปล่อยว่างเพราะคำนวณเอา
  check (mode = 'system' or limit_amount is not null)
);

-- เพดานที่ตรึงไว้ของแต่ละงวด + สถานะการเตือน
create table spending_limit_periods (
  id           uuid primary key default gen_random_uuid(),
  user_id      uuid not null references users(id) on delete cascade,
  period       text not null check (period in ('daily','weekly','monthly')),
  period_start date not null,
  limit_amount numeric(12,2) not null check (limit_amount > 0),
  alerted_80   boolean not null default false,
  alerted_100  boolean not null default false,
  unique (user_id, period, period_start)
);
```

ต้องเปิด RLS ทั้งสองตารางเหมือนตารางอื่น (§8) และทุก query กรอง `user_id` (G6)

## S5.10.8 หน้าเว็บ

- `settings.html` — ตั้งค่าทั้ง 3 ระดับ (เลือกโหมด + กรอกตัวเลขเมื่อเป็น manual)

## ข้อที่ต้องยืนยันกับทีม

1. **รายเดือนไม่ตรึง แต่รายวัน/รายสัปดาห์ตรึง** — ผมเลือกแบบนี้เพราะรายรับเข้ากลางเดือน
   ถ้าทีมอยากให้ตรึงทั้งสามเหมือนกัน ต้องตอบก่อนว่ารายรับที่เข้าหลังวันที่ 1 จะจัดการยังไง
2. **เพดานขัดกันเอง** เช่นตั้งรายวัน ฿300 (×7 = ฿2,100) แต่รายสัปดาห์ ฿1,500
   ผมเสนอให้ **เตือนตอนตั้งค่า แต่ไม่ห้าม** เพราะผู้ใช้อาจตั้งใจ
3. **ตั้งเพดานกลางงวด** เช่นตั้งรายสัปดาห์ตอนวันพุธ — ผมเสนอให้นับยอดที่ใช้ไปแล้ว
   ตั้งแต่วันอาทิตย์ที่ผ่านมาเลย (ไม่เฉลี่ยตามวันที่เหลือ) เพราะอธิบายง่ายกว่า
4. **โหมด `system` ทั้งสามระดับจะเตือนใกล้ๆ กัน** เพราะทุกระดับมาจาก R ตัวเดียวกัน
   การตรึงช่วยให้แยกกันได้ระดับหนึ่ง แต่ไม่ได้เป็นอิสระต่อกันจริงเหมือนโหมด `manual`
   — ทีมควรรู้ข้อจำกัดนี้ก่อนเริ่มทดสอบ
